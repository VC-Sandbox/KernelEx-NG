# 5. Module reference

Every C file of `kexnt.dll` (in `new_stubs/`), grouped by topic. The text under each file is that file's own header
comment. It says what the module provides, **which program and which measured failure led to it**, and how it
behaves. Dates and build numbers show when the module was added. Read the file itself for the details.

Rules that apply to every module:
- **Emulate where Windows 98 has the data.** Otherwise **fail with the error NT itself returns** for "not
  supported here". Never return success with garbage.
- Only KERNEL32/ADVAPI32 are imported. Every other system DLL is reached with `kex_sysproc()`.
- Windows 98 programs never reach these functions; the [gates](03-Architecture.md#gates-windows-98-programs-are-left-alone)
  send them to the previous implementation.

### `gate_ext.c` (200 lines)

```text
gate_ext.c - KernelEx-NG build 89: kexnt only for programs built for newer Windows.

KEXNT is in every core.ini configuration, including KernelEx's "Default mode" (DCFG1) that every 32-bit
program gets unless KernelEx is disabled for it - so Windows 98 programs went through kexnt's versions of
ReadFile, CreateFileMapping, the USER32/GDI32 calls, ... too. Now every function kexnt publishes through the
KernelEx resolver is a small gate (gen_apitable.py):
  - a program built for Windows NT 5 or later (the EXE's subsystem version 5.0+, as Chromium, Firefox, Mypal),
    or one the user gave an NT profile on the KernelEx tab (AppSettings\Configs, anything but Default mode /
    Windows 95 / 98 / ME / Disable custom heap): kexnt's function, as before (one compare and a jump);
  - any other program (Windows 98 programs: subsystem 4.x): what KernelEx gives WITHOUT kexnt - kexbasen,
    kexbases or the system DLL itself. Only a function that exists nowhere else (an NT-only call such a
    program looked up by name) still reaches kexnt; kexnt then sets itself up on that first call.
In a Windows 98 program kexnt's DllMain does nothing: no TLS slots, no hooks, no logs.
Override for tests: HKLM\Software\KernelEx\KexNG "Gate" = DWORD 0 (every program counts as modern).
KEXTEST.EXE exports "KexNG_ModernProcess" so it is always tested as a modern program.
MS-DOS and 16-bit Windows programs are never touched by KernelEx at all.
```

### `kexnt_crt.c` (58 lines)

```text
kexnt_crt.c - the few C library functions kexnt.dll needs, so it links WITHOUT msvcrt.dll.

Why: KernelEx initializes api libraries (FLoadTreeNotify on each) BEFORE the program's own DLLs.
If kexnt.dll imported msvcrt.dll, msvcrt's DllMain would run during kexnt's init, call TlsAlloc,
and get KernelEx's kexbasen TlsAlloc_new before kexbasen's own init has set its TlsLock ->
_EnterSysLevel(NULL) page fault in KERNEL32 (seen on Win98 SE, 86Box + VMware, 2026-10-31).
kexnt.dll must therefore import only KERNEL32/ADVAPI32 (shared-arena DLLs, never re-routed).
```

### `loader_ext.c` (260 lines)

```text
loader_ext.c - KernelEx-NG: LoadLibrary* for NT6+/Windows 10 callers on Windows 98 SE.
```

### `tls_ext.c` (376 lines)

```text
tls_ext.c - KernelEx-NG: static (implicit, __declspec(thread) / thread_local) TLS for DLLs loaded
with LoadLibrary on Windows 98 SE.

Windows 98 sets up the TLS directory (IMAGE_DIRECTORY_ENTRY_TLS) only for the exe and the DLLs
loaded with it at process start. A DLL loaded later with LoadLibrary is mapped and run, but its
TLS index variable is left at its file value (0) and no thread gets a copy of its TLS template,
so the first thread_local access reads another module's slot. Windows Vista and later handle this
case (chrome.dll relies on it, and has 6 TLS callbacks). Documented behaviour reproduced here:

  - a TLS slot is allocated (TlsAlloc) and written to the module's AddressOfIndex;
  - every thread gets its own block: template (StartAddressOfRawData..End) + SizeOfZeroFill zero
    bytes, aligned as the TLS Characteristics ask, stored in that slot. Compiled code reads it as
    fs:[2Ch][index] - on Windows 98 fs:[2Ch] is the same per-thread slot array TlsSetValue writes;
  - threads that already exist get a block too (as on Vista+), written into their slot array
    directly (found through the thread ID -> TDB -> TIB);
  - TLS callbacks run with DLL_PROCESS_ATTACH after the load, and with DLL_THREAD_ATTACH /
    DLL_THREAD_DETACH from kexnt's own thread notifications.

Which modules need it: a module list (toolhelp) is taken at the first LoadLibrary call; modules in
it were set up by Windows. Any module that appears later and has a TLS directory is set up by us -
that also covers the DLLs a loaded DLL pulls in through its imports.

Windows runs a DLL's entry point inside LoadLibrary. When kexnt's DLL-entry hook is live (veh_ext.c),
kex_tls_early sets the module up just before its DLL_PROCESS_ATTACH, as NT does; otherwise (hook not
installable) the setup happens after LoadLibrary returns.
```

### `reloc_ext.c` (114 lines)

```text
reloc_ext.c - KernelEx-NG: base relocations of a DLL that Windows 98 moved but did not fix up.

2026-11-01: chrome.dll (277 MB image, preferred base 0x10000000) was loaded at 0x10010000 because one of our
own small DLLs sat at the linker default 0x10000000 - and none of its 10 MB of relocations had been applied
(code pushed the unrelocated address of the CRT initializer table; the TLS callback array pointer was the
preferred-base value). Our DLLs now have their own bases (dll_base.py), so this should not recur for
chrome.dll; this is the safety net for any big DLL that still gets moved.

Called by the DLL-entry hook (veh_ext.c) just before a DLL loaded through kexnt's LoadLibrary gets
DLL_PROCESS_ATTACH. If the module is not at the base its file asks for, up to 64 HIGHLOW fixup sites spread
over the relocation table are compared with the file:
   memory == file + delta  -> applied by Windows: nothing to do
   memory == file          -> not applied
Only when every readable sample is "not applied" does kexnt apply the whole table (NT's own algorithm:
add delta at every IMAGE_REL_BASED_HIGHLOW site). Mixed results: nothing is touched, it is only logged.
```

### `peb_ext.c` (538 lines)

```text
peb_ext.c - KernelEx-NG: NT process environment block (PEB) for Windows 10 binaries on Windows 98 SE.

Windows NT code reads the PEB directly: `mov reg, fs:[30h]` then fields such as
ProcessParameters (+0x10), ProcessHeap (+0x18), NtGlobalFlag (+0x68), OS version (+0xA4..).
On Windows 9x fs:[30h] is the process database (PDB98) instead; e.g. PDB+0x10 is
TerminationStatus (0x103 = STILL_ACTIVE), so ucrtbase's thread start dereferenced 0x10B.

fs:[30h] cannot simply be re-pointed: KernelEx itself (get_pdb() = `mov eax, fs:30h`) and
Win98 KERNEL32 (AllocConsole reads TDB->tib.pProcess) depend on it. Instead every module that
targets Windows NT 6+ (OptionalHeader.MajorOperatingSystemVersion or MajorSubsystemVersion >= 6)
is patched once, before its code runs:
    64 A1 30 00 00 00        mov eax, fs:[30h]      ->  E8 <kex_peb_eax>  90
    64 8B xx 30 00 00 00     mov r32, fs:[30h]      ->  E8 <kex_peb_r32>  90 90
    64 A1 18 00 00 00 8B 40 30   mov eax, fs:[18h] ; mov eax, [eax+30h]  ->  E8 <kex_peb_eax> 90 x4
    (and the same with any register, when both instructions use the same one; clang emits only
     this two-step TEB->PEB form, so it is the one Chromium uses)
The helpers load the address of the emulated PEB below (no flags touched, like the original mov).
Rare forms (cmp/push with fs:[30h], fs:[18h] -> [other reg+30h]) are counted, not patched yet.

Who calls the patcher: every api-ms-win-*.dll shell in its DLL_PROCESS_ATTACH (it runs before the
DllMain of any module that imports it), plus kexnt's own process attach.
Win98 modules, KernelEx and anything in the shared arena (>= 0x80000000) are never touched.
```

## Threads, synchronization and exceptions

### `sync_ext.c` (404 lines)

```text
sync_ext.c - KernelEx-NG Phase 2: NT6+ synchronization primitives for Windows 98 SE.

Win98 has no keyed events and no futex, so everything is built on one primitive:
a "parking lot" (kex_park / kex_unpark) = hash table of wait queues keyed by address.
Each waiting thread sleeps on its own auto-reset event (created lazily, kept in TLS,
closed on DLL_THREAD_DETACH). The value check and the enqueue happen under the
bucket lock, and wakers modify the value BEFORE taking the bucket lock, so a wake
can never be lost (classic futex contract).

On top of it:
  WaitOnAddress / WakeByAddressSingle / WakeByAddressAll   (exact semantics)
  SRW locks       - pointer-sized word: bit0 exclusive, bit1 waiters, bits2+ shared count
  Condition vars  - pointer-sized sequence counter + park on it
  InitOnce        - pointer-sized: 0 / 1 sync-in-progress / 3 async-in-progress / ctx|2 done

Known limits (documented in ARCHITECTURE.md):
  - SRW is reader-preferring (a stream of readers can delay a writer); no recursion
    detection (same as NT: recursive acquire deadlocks).
  - Build 61: SRW release wakes ONE exclusive waiter (or every waiting reader when the first in the queue
    is a reader) and keeps the waiter bit while others remain queued. The old wake-all made every release of
    a contended lock (Chrome's thread-pool / allocator locks: the build-60 dump had 12 threads parked on SRW
    locks at once) wake all of them; on one CPU each woke, lost the race and parked again.
```

### `fls_ext.c` (131 lines)

```text
fls_ext.c - KernelEx-NG Phase 2: Fiber Local Storage for Windows 98 SE.

Every MSVC CRT since VS2005 calls FlsAlloc at startup (per-thread CRT data with a
destructor callback), so this blocks process start for Chromium and most modern apps.

Model: one Win98 TLS slot points to a per-thread block of FLS_MAX values. Blocks are
linked in a global list so FlsFree can run the callback for every thread's value
(NT semantics). On DLL_THREAD_DETACH the callbacks run for the exiting thread.

Limitation: storage is per THREAD, not per fiber (Win98 fibers share it). Chromium
does not combine fibers with FLS; documented in ARCHITECTURE.md.
Callbacks are not run at process exit (DLL_PROCESS_DETACH with lpReserved != NULL):
the DLL owning the callback may already be unmapped; NT's behaviour here is not
relied on by the CRT, which only frees memory in it.
```

### `veh_ext.c` (1522 lines)

```text
veh_ext.c - KernelEx-NG: vectored exception handling (AddVectoredExceptionHandler & co.) on Windows 98 SE.

Windows 98 SE has one user-mode exception dispatcher in KERNEL32 (4.10.2222: 0xBFF87ED3), found by RE of
the CD's kernel32.dll:
  - software:  RaiseException -> 0xBFF767D3 -> 0xBFF76745 -> 0xBFF9DA0B -> dispatcher(ctx, rec, -1, 0)
  - hardware:  KERNEL32's ring-0 callback sets Client_EIP = dispatcher (`mov [esi+24h], imm32` on a
               VMM Client_Reg_Struc) and builds [fake ret][ctx][rec][..][..] on the user stack.
Prologue: 55 / A1 <&pCurTDB> / 8B EC  (push ebp; mov eax,[pCurTDB]; mov ebp,esp).
The dispatcher later calls a "continue with CONTEXT" routine (VxDCall 0x2A0015) when a debugger handled
the exception; we use the same routine when a vectored handler returns EXCEPTION_CONTINUE_EXECUTION.

Hook (installed once per boot, system wide, because KERNEL32 is shared):
  dispatcher+0: E9 <stub> 90       (written with one cmpxchg8b: atomic on the uniprocessor 9x kernel)
  stub (KernelEx shared heap, permanent):
      push eax
      mov eax,[ppdbCur]; mov eax,[eax]          ; [ppdbCur] -> cell -> current PDB (two loads)
      mov eax,[eax+pdb_off]                      ; PDB_KEX.kex_storage (0C4h in KernelEx 4.5.2 and 4.6)
      test eax,eax / jz orig
      mov eax,[eax+slot_off]                     ; our slot (4*idx): this process's VEH entry, or 0
      test eax,eax / jz orig
      xchg eax,[esp] / ret                       ; jump to the per-process entry, eax restored
  orig: pop eax
  orig2: push ebp / mov eax,[pCurTDB] / jmp dispatcher+6
The fast path only does plain loads: no locks, no allocation (exceptions can happen anywhere).
Processes without VEH registrations (every Win98 program) take the orig path.

Per process: kex_veh_entry (below) calls the registered handlers; EXCEPTION_CONTINUE_EXECUTION resumes
at the (possibly modified) CONTEXT through KERNEL32's continue routine, anything else falls through to
the normal 9x path (debugger, SEH frames, UnhandledExceptionFilter).

Limits: vectored CONTINUE handlers run only after a vectored exception handler returned
CONTINUE_EXECUTION (NT also runs them after frame handlers do). Exceptions raised inside a vectored
handler skip VEH (per-thread recursion guard). Unknown KERNEL32 builds: nothing is patched,
AddVectoredExceptionHandler still succeeds but the handlers are never called (logged once).
```

### `wait_ext.c` (270 lines)

```text
wait_ext.c - thread-pool waits: RegisterWaitForSingleObject(Ex), UnregisterWait(Ex) (2026-11-10, builds 29-30),
plus DeleteTimerQueueTimer's completion event.

KernelEx 4.5.2 (kexbases ThreadPool.c) has two problems Chromium runs into:
 - UnregisterWaitEx(wait, hEvent) never signals hEvent when no callback is pending (NT always does).
   Chromium's base::win::ObjectWatcher::StopWatching waits on that event: build 28's thread snapshot showed
   "NetworkService" stuck there forever, so no page could load.
 - Once waits really get unregistered, its wait threads race (APC-driven list edits while a wait is in
   progress, items freed twice): build 29 died 15 s in with a stack overflow in WaitThreadProc ->
   WaitThreadWait, alloca(nItems * 8) with a corrupted negative nItems.
So kexnt has its own implementation:
 - waits live in a fixed table of slots (never freed memory: a wait thread that still holds a slot number
   from before an unregister finds it stale by its generation count, under the lock);
 - wait threads, each watching up to 62 objects plus its own wake-up event; a thread rebuilds its handle
   list whenever the set changes; the same handle is never put twice into one thread's list;
 - WT_EXECUTEINWAITTHREAD callbacks run on the wait thread, others through QueueUserWorkItem;
   WT_EXECUTEONLYONCE removes the wait before its callback runs; timeouts are handled per wait;
 - UnregisterWaitEx: NULL = don't wait (ERROR_IO_PENDING while a callback runs), INVALID_HANDLE_VALUE = wait
   for running callbacks (except from inside its own callback), an event = signalled when the last callback
   has finished (at once if none runs) - the NT rules.
```

```text
build-28 thread snapshots exist but need TRACEON, take the log lock (a hung thread may hold it), use
Toolhelp and GetModuleFileName (both take KERNEL32's own lock - a thread hung inside the loader holds that).

This one is always on in the main process of an NT 6+ program (command line without "--type="): 30 s and
75 s after start, if nothing has been drawn yet (no SwapBuffers / BitBlt / StretchDIBits / SetDIBitsToDevice
went through the GDI guard), it writes KEXHANG_<program>.LOG next to the program. Threads come from kexnt's
own list (DLL_THREAD_ATTACH + the thread that armed the logger), each stopped only for GetThreadContext.
Module names come from the image's own export directory, found through VirtualQuery - no KERNEL32 lock is
taken. Only at the very end does it ask Toolhelp for threads it did not know (that call may block; by then
the file has everything else).
```

### `prof_ext.c` (732 lines)

```text
prof_ext.c - KernelEx-NG: "where does the time go" for a slow program (2026-11-02, Mypal on YouTube).

Switched on by HKLM\Software\KernelEx\KexNG "Profile" (DWORD) = 1 (PROFON.REG / PROFOFF.REG on the test CD).
A sampler thread wakes every 25 ms (10 ms until build 104: it then cost up to 16-19% of the time), stops each thread of the process for a moment (SuspendThread +
GetThreadContext, as Mozilla's own hang monitor does), notes where it was (EIP) and lets it go on. When the
program exits (or crashes), KEXPROF_<program>.LOG next to it gets:
  - time per module (xul.dll = page layout/scripts, js JIT code shows as "(no module)", GDI32/USER32 and the
    16-bit GDI.EXE/USER.EXE = Windows drawing, KEXBASES/KEXBASEN/KEXNT = KernelEx itself, ...)
  - time per thread (main thread vs Compositor vs decoders ...)
  - the 60 hottest code addresses (module + offset, 16-byte buckets)
  - every GDI32/USER32 call that went through kexnt's guard: count and CPU cycles (RDTSC).
Between Suspend and Resume the sampler only calls GetThreadContext - no heap, no locks.
```
